This layout lets one Google OAuth client serve many Amazon Cognito user pools through one stable
oauthmux callback. Each pool talks to the same oauthmux instance for authorization and token
exchange, then validates Google's ID token and obtains claims from Google's UserInfo endpoint.

## Why oauthmux fits this topology

Google sees one OAuth client and one allowed redirect URL regardless of how many Cognito pools use
it:

```text
https://login.example.com/oidc/google/callback
```

oauthmux remembers which validated Cognito `/oauth2/idpresponse` URL started each flow and returns
the result to that pool. All participating pools share the Google client ID, consent boundary,
scopes, and oauthmux downstream client credential. Their callback origins remain explicit in the
oauthmux allow-list.

Use one oauthmux instance for this shared Google client. Creating an instance per pool produces a
different oauthmux callback per instance and removes the single-callback benefit. Separate
instances are appropriate when pools require independent Google clients, scopes, or operational
isolation.

## The three configurations

### 1. Google OAuth client

Create a web OAuth client in the Google project. Register exactly the stable callback for the
shared oauthmux instance:

```text
https://login.example.com/oidc/google/callback
```

The client needs the OpenID Connect scopes Cognito will request, normally `openid`, `email`, and
`profile`. Keep the Google client ID and secret available for both the oauthmux upstream
configuration and the Cognito provider configuration.

### 2. oauthmux instance

Configure Google as the upstream issuer and permit the hosted-domain origin of every participating
Cognito pool. The shared-secret client authentication values match the credentials each pool
sends to oauthmux's token endpoint.

```yaml
instances:
  google:
    issuer_url: https://accounts.google.com
    authorization_endpoint: https://accounts.google.com/o/oauth2/v2/auth
    token_endpoint: https://oauth2.googleapis.com/token
    jwks_uri: https://www.googleapis.com/oauth2/v3/certs
    client_id: 123456789.apps.googleusercontent.com
    client_secret: ${GOOGLE_CLIENT_SECRET}
    scopes: [openid, email, profile]
    allowed_scopes: [openid, email, profile]
    allowed_redirect_origins:
      - https://pool-a.auth.eu-west-1.amazoncognito.com
      - https://pool-b.auth.us-east-1.amazoncognito.com
      - https://login.product.example
    client_auth:
      mode: client_secret
      client_id: 123456789.apps.googleusercontent.com
      client_secret: ${GOOGLE_CLIENT_SECRET}
```

The allow-list contains origins, not paths. A pool's actual redirect ends in
`/oauth2/idpresponse`, and oauthmux validates its origin before starting the flow.

### Store the shared instance in SSM

For Lambda deployments, the SSM provider is a good fit for an allow-list that changes as Cognito
pools are created. Store one SecureString parameter named `/oauthmux/instances/google`; its value
is the `google` instance document above without the outer `instances` and `google` keys. Add each
pool origin to that single document rather than creating one oauthmux instance per pool. Replace
the `${GOOGLE_CLIENT_SECRET}` references with the secret value inside the encrypted parameter;
the SSM provider receives the decrypted document and does not expand environment variables.

oauthmux loads the initial snapshot during Lambda cold start. A warm execution environment checks
the snapshot age before every invocation and synchronously reloads providers once it reaches
`OAUTHMUX_LAMBDA_CONFIG_TTL`, which defaults to `60s`. A failed SSM refresh keeps the last valid
snapshot. Consequently, an SSM update normally becomes visible to each active environment on its
first invocation after the TTL expires; no background timer is required while Lambda is frozen.

### 3. Cognito OIDC provider

Add an OIDC provider to each user pool using manual input. Keep trust fields pointed at Google and
route only the authorization and token fields through the shared oauthmux instance.

```json
{
  "ProviderDetails": {
    "client_id": "123456789.apps.googleusercontent.com",
    "client_secret": "<Google OAuth client secret>",
    "authorize_scopes": "openid email profile",
    "oidc_issuer": "https://accounts.google.com",
    "authorize_url": "https://login.example.com/oidc/google/authorize",
    "token_url": "https://login.example.com/oidc/google/token",
    "attributes_url": "https://openidconnect.googleapis.com/v1/userinfo",
    "attributes_request_method": "GET",
    "jwks_uri": "https://www.googleapis.com/oauth2/v3/certs"
  }
}
```

Map the Google claims Cognito needs, enable this provider on the intended user-pool app client,
and include it in the hosted UI's identity-provider choices.

## Correctness checks

- Google lists the oauthmux callback, not Cognito's `/oauth2/idpresponse`, as its redirect URI.
- oauthmux allows the exact hosted-domain origin of every participating pool.
- Cognito's issuer, JWKS, and UserInfo fields point directly to Google.
- Cognito's authorization and token fields point to the same oauthmux instance.
- The Google client ID is Cognito's provider client ID so the Google ID token audience is valid.

oauthmux forwards Cognito's nonce to Google and returns Google's token response unchanged. Cognito
therefore validates the nonce, audience, issuer, and signature against the identity Google issued.

See the [Google OpenID Connect documentation](https://developers.google.com/identity/openid-connect/openid-connect)
and [Cognito OIDC provider documentation](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-oidc-idp.html)
for the provider-side settings represented here.
