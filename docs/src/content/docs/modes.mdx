Endpoint ownership and token trust are separate decisions. oauthmux has two operating models with
different security boundaries.

## Transparent relay

<Mermaid
  label="Transparent relay sends authorization and token traffic through oauthmux while the relying party trusts the upstream issuer."
  chart={`flowchart LR
    RP[Client or relying party]
    M[oauthmux]
    U[Upstream issuer]

    RP -->|authorize and token| M
    M -->|authorization and code exchange| U
    U -->|upstream-signed response| M
    M -->|unchanged response| RP
    RP -.->|trust issuer and JWKS| U`}
/>

Transparent relay is available. oauthmux owns the stable callback, authorization state, PKCE
exchange, redirect policy, and the relayed authorization and token endpoints. The token response
is byte-for-byte upstream output, so its `iss`, signature, JWKS, audience, and UserInfo contract
remain upstream-owned.

Use this mode when the relying party supports manual OIDC endpoints. Configure its issuer, JWKS,
and UserInfo URLs from the upstream provider, then point only its authorization and token URLs at
oauthmux. Amazon Cognito is a useful example because its OIDC provider configuration exposes all
of those fields independently.

:::caution
Metadata served below an oauthmux URL preserves the upstream `issuer` and `jwks_uri` and rewrites
the authorization and token endpoints. It is useful as relay metadata, but it is not a portable
OIDC Discovery contract: standard discovery requires the metadata URL and advertised issuer to
identify the same issuer.
:::

## Brokered issuer

<Mermaid
  label="Brokered issuer validates upstream identity and creates a new oauthmux-signed identity trusted by the relying party."
  chart={`flowchart LR
    RP[Client or relying party]
    M[oauthmux]
    U[Upstream issuer]

    RP -->|authorize and token| M
    M -->|authorization and code exchange| U
    U -->|upstream-signed response| M
    M -->|new oauthmux-signed response| RP
    M -.->|validate upstream issuer and JWKS| U
    RP -.->|trust oauthmux issuer and JWKS| M`}
/>

Brokered issuer is planned. In this model oauthmux validates the complete upstream identity and
issues a new downstream identity with its own issuer, audience, signature, JWKS, and UserInfo
contract. The relying party trusts oauthmux rather than the upstream provider.

Use this mode for relying parties that require standard discovery from the oauthmux URL or cannot
configure transport endpoints separately from issuer metadata. It adds a signing-key lifecycle
and makes oauthmux an identity issuer, so it is intentionally a distinct mode instead of a relay
setting.

## Choosing a mode

| Requirement | Mode |
| --- | --- |
| Preserve upstream-signed tokens and claims | Transparent relay |
| Configure authorization and token URLs independently | Transparent relay |
| Discover oauthmux as the issuer | Brokered issuer |
| Give oauthmux control of downstream claims and audience | Brokered issuer |

Do not configure oauthmux as the issuer for an unchanged upstream token. An issuer claim names the
authority that signs and vouches for that token, not the service that transported it.
